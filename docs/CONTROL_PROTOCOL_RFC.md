# ConfFlow Control Protocol RFC v1

## Status and scope

This RFC freezes the future `confflow control ... --json` one-shot protocol.
Phase C's internal `ExecutionService` core and in-memory contract repository
are implemented and tested, but no control CLI, normal-CLI adapter, agent
adapter, production persistence adapter, or capability-payload change is
implemented.  The current `confflow` CLI, `confflow-agent`, workflow engine,
and capability v4 payload therefore remain unchanged in this phase.

This v1 revision is still pre-publication. It replaces the earlier locator-free
draft; the v1 identifiers become immutable only when this design gate is
accepted and published.

The normative JSON Schema bundle is in `docs/control_protocol/v1/`.  Golden and
negative examples are in `tests/fixtures/control_protocol/v1/` and are validated
by `tests/test_control_protocol_schema.py`.

## Ownership and boundary

| Data or transition | Authoritative owner | JobDesk responsibility |
| --- | --- | --- |
| user intent, upload, submit journal, scheduler selection | JobDesk | persist and recover the local operation |
| prepared record, execution state, revision, events, checkpoint, artifacts | ConfFlow | consume a monotonic projection only |
| executable/build/install provenance | ConfFlow produces; JobDesk validates | persist accepted snapshot and digest |

`run_id` is generated by JobDesk and is identical on both sides.  JobDesk never
reads or writes the agent SQLite database.  ConfFlow never chooses a scheduler:
JobDesk uploads inputs under the selected state root, calls `prepare`, durably
stores the returned handle and resolved root, and then launches `execute` through
its existing nohup, Slurm, or PBS mechanism.
`prepare` must not start a calculation and `execute` must not daemonize itself.

## Commands

The future adapter has these commands.  They are protocol names only in this
phase; no command parser is added by this RFC.

```text
confflow control capabilities --json
confflow control prepare --state-root <absolute-path> --request <request.json> --json
confflow control execute --state-root <absolute-path> --run-id <id> --json
confflow control status --state-root <absolute-path> --run-id <id> --json
confflow control events --state-root <absolute-path> --run-id <id> --after <cursor> --json
confflow control cancel --state-root <absolute-path> --run-id <id> --json
confflow control resume --state-root <absolute-path> --run-id <id> [--checkpoint <id>] --json
confflow control artifacts --state-root <absolute-path> --run-id <id> --json
```

Every request and response uses `protocol_schema: "confflow.control.v1"`.  The
v1 string and every v1 schema `$id` are frozen.  Any new field, error code, or
semantic rule is a v2 protocol release with new `$id` values; there is no v1
minor-extension or partial minor-negotiation policy.  Unknown protocol strings
fail closed.

## Repository and staging locator

All stateful commands resolve one state root with this strict precedence:
explicit `--state-root`, then `CONFFLOW_CONTROL_STATE_ROOT`, then the absolute
`$XDG_STATE_HOME/confflow/control`, then `$HOME/.local/state/confflow/control`.
CLI and environment values must already be absolute POSIX paths; relative values
are usage errors and are never resolved against the current directory. A set but
relative `XDG_STATE_HOME`, or a missing/non-absolute `HOME` when it is needed, is
also a usage error rather than a silent fallback. JobDesk
must always pass the explicit absolute value and persist the resolved identity in
its submit journal; environment/default resolution is for interactive use only.

One SQLite file is the authority for every run in the root:

```text
<state-root>/v1/repository.sqlite3
<state-root>/v1/runs/<run_id>/staging/
<state-root>/v1/runs/<run_id>/work/
```

The single repository is required so `(repository, idempotency_key)` uniqueness
is transactional across different run IDs. It records the resolved state-root
identity and rejects an open through an incompatible alias or different root.
The repository path and root identity are not part of `request_digest`.

The root is created mode `0700`, must be owned by the effective user, and must
not be `/`, the home directory itself, or group/world writable. An
administrator-approved shared root may have managed permissions, but that
approval and its resolved identity must be recorded. Service-created run,
staging, work, and database paths are always derived from the root and safe
`run_id`; requests cannot supply an absolute work directory.

`workflow_config.path` and `input_manifest.path` are relative to the run's
`staging/` directory. They are canonical POSIX regular-file paths: no absolute
form, backslash, NUL, empty segment, `.`, `..`, double slash, or trailing slash.
Every component is opened relative to a trusted directory descriptor without
following symlinks, and the final object must be a regular file. Prepare verifies
raw byte digests before parsing and persists device, inode, size, and digest;
execute re-verifies the content digest before launch.

The input manifest uses `confflow.control.input-manifest.v1`. Its entries preserve
input order with zero-based contiguous `ordinal`, and carry relative path,
SHA-256, and size. Phase C enforces contiguous unique ordinals, normalized path
uniqueness, regular-file type, size, and digest. Config and input contents are
not embedded in the request, and digest-only filenames are not used: verified
relative locators retain upload auditability without duplicating large content.

## State, revision, and events

| From | Allowed transitions | Notes |
| --- | --- | --- |
| `prepared` | `queued`, `cancelled` | `prepare` is durable but non-executing |
| `queued` | `running`, `cancelled`, `failed` | scheduler metadata is a JobDesk projection |
| `running` | `paused`, `completed`, `failed`, `cancelled` | terminal states never regress |
| `paused` | `queued`, `cancelled`, `failed` | `resume` validates the checkpoint |
| `completed`, `failed`, `cancelled` | none | terminal |

Each successful mutation assigns a strictly greater integer `revision`.  A
snapshot with a lower revision must not overwrite a newer JobDesk projection.
Events have stable opaque cursors.  `events --after <cursor>` returns events
strictly after that cursor in ascending revision/cursor order. `next_cursor` is
the cursor of the final returned event, or repeats the supplied cursor for an
empty page; it is `null` only on the initial empty page.  An unknown or expired
cursor returns a typed error, never an inferred file offset.

## Idempotency and recovery

`prepare` requires an idempotency key and request digest.  The same key and
digest returns the original prepared handle; the same key with a different
digest returns `idempotency_conflict`.  If ConfFlow accepts `prepare` but
JobDesk fails before persisting its journal, JobDesk repeats `prepare` with the
same key and then persists the returned handle, or explicitly cancels a still
`prepared` run.  It must not submit a second payload.

`request_digest` is lowercase SHA-256 over RFC 8785 JCS canonical bytes for the
complete request object with only `request_digest` omitted. It therefore covers
`protocol_schema`, `operation`, `run_id`, `idempotency_key`, both locator paths
and digests, and every supplied executable-identity field. The input file list is
transitively bound by the verified input-manifest digest. The effective state
root is excluded; its namespace and resolved identity are persisted by the
repository. Both `idempotency_key` and `run_id` are unique in that repository:
same key and digest returns the handle, while either identifier reused with a
different payload fails closed.

`execute` is idempotent per `run_id`: the first accepted launch must atomically
advance `prepared` to `queued` and return that queued snapshot. Every duplicate
returns the same run's current snapshot and must not create a second calculation
process. A duplicate may therefore return `queued`, `running`, `paused`,
`completed`, `failed`, or `cancelled`; it cannot return `prepared` after an
execute was accepted. A duplicate execute never uses `already_running`; that
code is reserved for a non-idempotent operation that v1 explicitly rejects.

The JobDesk journal is authoritative for upload, prepare, launcher start, and
remote-acceptance checkpoints.  ConfFlow is authoritative from its durable
prepared record onward.  Neither side may use an older projection to roll back
the other side's state.

## Typed errors

Responses use `error.code` for branching and reserve `error.message` for people.
The v1 registry is: `invalid_request`, `unsupported_protocol`, `unknown_run`,
`idempotency_conflict`, `invalid_state_transition`, `invalid_checkpoint`,
`already_running`, `terminal_run`, `executable_identity_mismatch`,
`artifact_path_invalid`, `artifact_integrity_failed`, `repository_unavailable`,
and `internal`. `repository_unavailable` covers an unsafe root, failed ownership
or lock guarantees, root identity mismatch, and unavailable shared storage. New
codes require protocol v2.

## Artifact safety

`artifacts` is visible only in a terminal state (`completed`, `failed`, or
`cancelled`) and returns producer-validated paths only. Every artifact path is a
canonical regular-file relative POSIX path: it has no empty segment, `.`, `..`,
double slash, trailing slash, or absolute form. Each entry includes digest and
size. JSON Schema cannot express array-wide uniqueness after path normalization.
Therefore Phase C must normalize every target and reject duplicate
`(terminal, path)` pairs or two entries that normalize to the same target with
the stable `artifact_path_invalid` error before an adapter exposes the manifest.
JobDesk verifies digest and size after SFTP download.

## Capability advertisement (future change)

Capability v4 is intentionally unchanged here.  The future producer change
will add a separately versioned, machine-readable control-protocol declaration
only after this RFC and its fixture review are accepted.  JobDesk must negotiate
that declaration before selecting the control backend; absence means legacy
shell/file backend.  This RFC neither reserves a capability v4 field nor changes
the current payload.

## Phase C conformance sequence fixtures

Before a service or adapter is accepted, Phase C must add executable sequence
fixtures for: monotonic revisions and terminal non-regression; ordered cursor
replay, empty-page `next_cursor`, and reconnect; same-key same-digest prepare;
same-key different-digest conflict; duplicate execute returning the current
snapshot without another process, specifically first execute = `queued` and
duplicate execute = the unchanged running or terminal snapshot; valid, missing,
stale, running, and terminal resume; and normalized artifact target conflicts.
These are cross-frame rules, not claims that a single JSON Schema instance can
prove.

Phase C also tests locator traversal, symlink substitution, config/manifest and
input digest changes between prepare and execute, state-root identity mismatch,
and cross-run idempotency conflicts in the single repository.

## Fixture manifest

`tests/fixtures/control_protocol/v1/manifest.json` is the normative list of
examples. Its `golden` and `negative` rows name each fixture and its validator.
The test rejects missing rows, unlisted files, duplicate rows, a mismatched
fixture `_schema` marker, a golden validation failure, or a negative validation
success. The marker is descriptive; the manifest selects the validator.

## Compatibility

The legacy JobDesk shell/file backend remains available for at least one released
compatibility cycle.  A run selects exactly one backend at creation; a fallback
cannot mix event/status sources during a run.  A later removal decision requires
real WSL validation for nohup, Slurm/PBS, reconnect, download, resume, and cancel.

JobDesk passes the same explicitly quoted `--state-root` to login-shell queries,
nohup launchers, and Slurm/PBS job bodies; it does not rely on scheduler-exported
environment. Same-host storage may use SQLite WAL. A scheduler job on another
host is supported only when the root is mounted at the same absolute path and an
administrator guarantees SQLite-compatible POSIX byte-range locks, atomic
create/rename, and fsync. Cross-host mode uses rollback-journal `DELETE`, a busy
timeout, and transactional `BEGIN IMMEDIATE`, never WAL. NFS, SMB, object/FUSE,
or any unverified shared filesystem fails closed with `repository_unavailable`;
a same-host probe cannot certify cross-host locking. If those guarantees are not
available, scheduler control remains disabled and JobDesk uses the legacy
backend until a daemon/RPC or non-SQLite repository is designed.
