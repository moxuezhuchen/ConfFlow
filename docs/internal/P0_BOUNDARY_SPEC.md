## 1. Version matrix

| Identity | Value | Meaning |
|---|---|---|
| Boundary protocol id | `confflow.boundary.v4` | one process boundary shared by every operation |
| Boundary protocol version | `1.0.0` | wire version of this document |
| Canonicalization id | `confflow.v4.jcs.v1` | RFC 8785 (JCS) over UTF-8 |
| Workflow schema id | `confflow.workflow.v4` | document edited and prepared |
| Semantics version | `confflow.workflow.v4.semantics.v1` | digest/wire semantics of the workflow line |
| Result manifest schema | `confflow.run_result_manifest.v1` | published result wire |
| Validation response schema | `confflow.configuration-validation.v1` | `v4 validate` answer |
| PreparedRun manifest schema | `confflow.prepared_run_manifest.v1` | immutable execution request (PR-3) |
| Validation receipt schema | `confflow.validation_receipt.v1` | frozen validation proof (PR-3) |
| Authoring protocol schema | `confflow.authoring.v4` | request/response of the authoring seam |
| Configuration contract schema | `confflow.configuration-contract.v4` | contract envelope |

Versions are independent axes: a build change moves none of them; a schema
change moves exactly the schema it changes plus the semantic identity digest.

## 2. Canonicalization (PR-0 JCS)

- Algorithm: RFC 8785 (JCS), UTF-8 bytes, SHA-256 digest.
- Numbers: ECMAScript `Number::toString`; `1.0` → `1`, `-0.0` → `0`, `1e-7` → `1e-7`.
- Integers beyond the IEEE-754 safe integer domain are rejected (`integer_out_of_domain`).
- Non-finite numbers are rejected (`non_finite_number`), including inside arrays/objects.
- Duplicate mapping keys are rejected (`duplicate_mapping_key`).
- Mapping keys sort by UTF-16 code units and are **never** Unicode-normalized
  (NFC and NFD spellings are distinct keys).
- Arrays keep order.

Producer CLI contract:

```jsonc
// ok
{"ok": true, "canonicalization_id": "confflow.v4.jcs.v1",
 "canonical_json": "...", "canonical_sha256": "<64 hex>"}
// rejected (exit code 1)
{"ok": false, "canonicalization_id": "confflow.v4.jcs.v1",
 "reason_code": "non_finite_number", "detail": "..."}
```

Domain-separated digests wrap the payload as
`{"canonicalization": "confflow.v4.jcs.v1", "kind": "...", "payload": ...}`;
the digest string form is `sha256:<64 lowercase hex>`.  Consumers use a
JCS-compatible implementation; they do not copy producer domain functions.

## 3. Step identity

- `WorkflowDocument.steps[].id` is the only business step identity.
- `label` is display only; duplicate labels are legal; reordering changes no identity.
- Duplicating a step allocates a new id.
- Bindings, diagnostics, resources, selection, and provenance address steps by V4 id.
- Array position and any `jd_*`-style parallel id are **never** identity.

## 4. Named binding wire

Bindings live under `steps[].bindings.<target_port>`:

```yaml
steps:
  - id: sp_1
    bindings:
      structure:
        source:
          step: opt_1     # or: run: structures
          port: structures
          select: { role: optimized, ids: [...] }   # optional
        cardinality: many          # optional; default from the port contract
        pairing: per_structure     # optional; default from the port contract
        partial_consumption: accept_subset  # optional
```

- `source` carries exactly one of `run` (named run input) or `step` + `port`.
- Producer-owned vocabulary: `SourceKind`, `Cardinality`, `Pairing`,
  `PartialConsumption`, `SelectorKind` (published in the contract `ports.vocabulary`).
- Selectors are only valid where the source port kind allows them (for example,
  a role selector applies to artifact ports, not structure ports).
- JobDesk edits this wire; it never builds its own compatibility table, port
  registry, or source guess.  The single-string `artifact_source` seam is retired.

## 5. Resource and scheduler wire

```yaml
global:
  resources: { cores_per_item: 8, memory_per_item: 16GiB }
  scheduler: { max_parallel_items: 2, on_failure: continue }
steps:
  - id: sp_1
    resources: { memory_per_item: 32GiB }   # per-field override only
```

- Step fields are **presence-preserving**: absent means "inherit", not "default".
  Writing `null` is not a clear; clearing a field deletes the key.
- Effective values resolve per field: step → global → schema default, through
  `ResourceRequest.with_defaults()` / `SchedulerPolicy.with_defaults()`.
- `cores_per_item`/`memory_per_item` are the execution resource request and
  participate in semantic identity.  `max_parallel_items` is scheduler policy
  and never changes scientific input.
- Server capacity is advisory only; a server never silently rewrites requested
  resources.

Effective-values example (PR-1 acceptance): global `8 / 16GiB / 2`, step memory
`32GiB` → effective `8 / 32GiB / 2`; clearing the step field restores `16GiB`.

## 6. Identities and relationships

```text
submission_id            client-authored idempotency key of one prepare attempt
snapshot_digest          digest over the frozen prepared snapshot bytes
run_id                   producer-allocated identity of one accepted run
generation_id            producer-allocated identity of one run/resume generation
receipt_digest           digest over the canonical validation receipt bytes
```

Rules:

- same `submission_id` + same `snapshot_digest` → the same admission/run (retry-safe);
- same `submission_id` + different `snapshot_digest` → rejected;
- "run again" allocates a new `submission_id`;
- resume is not submit-again;
- a superseded generation can never masquerade as current truth;
- validate reads the published snapshot; submit accepts only the same snapshot identity
  (any mismatch means zero native invocations);
- unsubmitted snapshots expire by TTL or explicit cleanup and are never executed.

Input identity separates four facts that must never be conflated:
`selection_id` (user selection), `content_sha256` (frozen bytes),
producer structure/subject ids, and the producer-owned opaque `locator`.
Preparation stages exact bytes and hashes the staged bytes; submit never
re-opens a source path.

## 7. Compatibility (not digest equality)

Vocabulary (`confflow v4 boundary --json` → `compatibility`):

- `compatible` — every requirement is satisfied and identities match;
- `needs_revalidation` — requirements hold, but content or build provenance moved;
- `unsupported` — a requirement is missing, version-incompatible, or unsatisfied
  (this dominates `needs_revalidation`).

Requirements: `{kind: capability|contract|semantic, name, contract_version}`.
Offered: capabilities/contracts from the contract envelope plus the semantics
version.  Reason codes are stable and listed in the boundary document.

Matrix:

| Change | Decision |
|---|---|
| recipe description / label / display metadata / ordering | `compatible` |
| producer build version/commit/dirty | `needs_revalidation` |
| capability contract version or port contract shape | `unsupported` |
| required capability removed | `unsupported` |
| workflow schema / semantics / canonicalization identity | `unsupported` |
| content identity moved, same schema and semantics | `needs_revalidation` |

Full `contract_key` equality is **not** the instantiation rule: a card
instantiates when the decision is `compatible` or `needs_revalidation` (the
latter requiring producer re-validation before submit), and only `unsupported`
refuses.  Content digests exist for integrity; they are not compatibility.

## 8. PreparedRun and validation receipt (published now, implemented in PR-3)

PreparedRun manifest (immutable execution request):

```json
{
  "content_schema": "confflow.prepared_run_manifest.v1",
  "submission_id": "...",
  "snapshot_digest": "sha256:...",
  "frozen_workflow_sha256": "sha256:...",
  "input_manifest": {"entries": [{"name": "structures", "selection_id": "...",
    "content_sha256": "sha256:...", "locator": "..."}], "digest": "sha256:..."},
  "execution_binding_digest": "sha256:...",
  "producer_provenance": {"package": "confflow", "version": "...", "commit": null, "dirty": null},
  "compatibility_requirements": [],
  "validation_receipt": {"receipt_schema": "confflow.validation_receipt.v1",
                         "receipt_digest": "sha256:..."}
}
```

Validation receipt: schema id, submission id, snapshot digest, workflow bytes
SHA-256, input manifest digest, execution binding digest, producer semantics
identity, producer build provenance, `ok`, diagnostics.  The JSON Schemas are
published in the boundary document and embedded in the contract by digest.

## 9. Authoring seam (wire frozen now, producer implementation PR-1)

One protocol, five operations: `describe_step`, `binding_candidates`,
`instantiate_card`, `validate_document`, `check_compatibility`.

Request: `{content_schema, operation, document | document_digest, parameters}`.
Response: `{content_schema, operation, ok, capability_identity,
request_document_digest, result, diagnostics}`.

`binding_candidates` returns, per candidate, `target_step_id`, `target_port`,
the source mapping, effective cardinality/pairing, compatibility status and
diagnostics, the request document digest, and the capability identity.
Automatic wiring is permitted only when the document still matches, the target
port is explicit, the producer returns exactly one complete legal binding, no
selector/pairing ambiguity exists, grouping is not guessed, all required ports
are satisfied, the response is fresh, and the applied document validates.

## 10. Error behavior

- Every machine failure is structured JSON on stdout with a stable
  `reason_code`/`code`; human text goes to stderr.
- Exit codes: `0` success/valid, `1` structured failure, `2` usage error.
- Consumers fail closed: unknown boundary protocol version, a missing required
  schema digest, or digest mismatch refuses the boundary; there is no fallback
  to legacy wire.  The required digest set covers the authoring schemas
  (`authoring_request`, `authoring_response`); the future-only PreparedRun
  manifest and validation receipt digests (§8, PR-3) are published by the
  producer and recorded by the consumer when present, but they are not required
  for boundary acceptance.
- Diagnostics carry `code`, `severity`, `message`, optional `step_id` and
  `field_path`; `step_id` is always a V4 step id or null.
