## V1 — P1：MLIP 后端初始化失败被发布为 completed，续跑持续复用空结果

位置：

- `confflow/execution/mlip_runner.py:236`：`_load_backend()` 捕获后端构造异常后返回 `_BrokenBackend`。
- `confflow/execution/mlip_runner.py:285`：`run_job()` 把错误写成逐结构 error row，最终返回 0，并写出完成文件。
- `confflow/execution/mlip_executor.py:910`：结果组装无条件返回 `WorkItemStatus.COMPLETED`，即使所有结构都因错误被丢弃。

触发：模型／后端初始化发生异常，例如临时资源不可用。它是整个计算后端没有成功建立，不能等同于某一个坏结构被筛除。

独立复现通过正常 `V4RunApplication.run()` 入口，使用真实 `mlip_runner.run_job()` 的加载、计算、错误行与完成文件协议，仅替换后端 factory 来控制一次临时初始化失败；没有替换 batch、持久化、发布或复用逻辑。模型文件、解释器、runner 源码和环境在同 root 的两次运行间保持不变。

| 操作 | 实测 run 状态 | 输出结构 / 能量条数 | 是否启动 runner |
| --- | --- | --- | --- |
| 后端初始化失败时首次运行 | completed | 0 / 0 | 是 |
| 恢复后端后，同 run root 续跑 | completed，带 reuse_hit | 0 / 0 | 否 |
| 恢复后的新 run root 对照 | completed | 1 / 1 | 是 |

影响：一次可恢复的基础设施故障变成永久可复用的空科学结果。run 的终态不能表达计算失败；仅修复环境中的临时故障并续跑无法恢复结果。

建议：后端初始化失败应作为任务级失败传到 executor，不能进入完成结果缓存。保留已有“个别结构失败后继续处理其他结构”和合法筛选得到空集合的语义，不应简单用“输出为空”覆盖所有情况。补充失败 → 恢复 → 同 root 续跑的公共入口测试，并覆盖单 worker 与多 worker 初始化失败。

证据：`runtime-results.json` 的 `backend_outage`；脚本 `runtime_probes.py`。

## V2 — P2：MLIP 和注册脚本丢失配置中的命令名，错误拒绝裸名白名单

位置：

- `confflow/execution/mlip_executor.py:508`：把配置的 `python3` 解析成绝对路径后，向策略检查的两个参数都传绝对路径。
- `confflow/execution/script_executor.py:266`：注册脚本解释器存在相同处理。
- 契约：`confflow/execution/execution_policy.py:33` 明确区分原始配置名与解析后的绝对路径，允许两种形式匹配。

复现：通过正常 V4 应用入口运行，MLIP 的 `execution.executable` 为 `python3`；脚本注册命令的解释器也是 `python3`。

| allowed_executables | MLIP | 注册脚本 |
| --- | --- | --- |
| `[python3]` | failed，解释器不被允许 | failed，解释器不被允许 |
| `[/usr/bin/python3]`（本机解析结果） | completed | completed |

影响：合法的白名单配置无法使用。此前 ConfGen 的裸名白名单修复没有覆盖这两个执行器。这是错误拒绝，本次没有证明越权启动。

建议：保留原始配置候选名，同时传递解析后的路径；不要通过无条件取 basename 来放宽绝对路径白名单。补充 native / ConfGen / script / MLIP 共用的策略契约测试，包含裸名允许、对应绝对路径允许、其他绝对路径拒绝，以及被拒时无启动。

证据：`runtime-results.json` 的 `mlip_allow_name`、`mlip_allow_absolute`、`script_allow_name`、`script_allow_absolute`、`script_launches`。

## V3 — P2：原生计算按控制进程 PATH 查找程序，忽略步骤环境的 PATH

位置：

- `confflow/application/v4_run.py:944`：预检使用没有显式 path 的 `shutil.which(candidate)`，随后才构造步骤环境快照。
- `confflow/execution/environment.py:193`：程序身份测量也按控制进程 PATH 解析裸名。
- `confflow/execution/work_item_executor.py:1142`：实际执行再次按控制进程 PATH 解析，再用该绝对路径启动。

复现：准备两个正常可启动的假 ORCA，控制进程 PATH 优先 `A/orca`，步骤 `execution.env.PATH` 优先 `B/orca`，`execution.executable: orca`。正常 V4 run 完成，但启动日志只有 `A`；按步骤环境应解析到 `B/orca`。

影响：用步骤 PATH 选择程序版本时，实际运行的是另一个安装版本；程序只存在于步骤 PATH 时也无法找到。显式配置绝对路径可规避。本次场景的测量和启动均指向 A，没有证明“测量 A、启动 B”或错误缓存复用，不能把它描述成此前 ConfGen 的同一个安全缺口。

建议：以冻结后的有效环境解析命令，且使策略校验、身份测量、实际启动使用同一次解析的结果。复用 ConfGen 已有的快照规则。修复时应同时覆盖允许 A／允许 B 的策略组合，防止只改启动路径后重新引入测量与启动不一致。

证据：`runtime-results.json` 的 `native_binding_path`。

## 架构判断

现有分层值得保留：domain 的不可变对象与摘要、workflow 的编译与组装、application 的 run/generation 编排、execution 的执行器和进程监管、persistence 的登记／复用／发布、producer 的外部契约与结果投影，职责已经较清楚。控制服务的 CAS、launch token、终态仲裁和 worker handoff 也提供了明确边界。没有发现需要据此开展整体重写的证据。

当前主要风险是跨执行器的共同规则仍在各处接线：原始命令名、实际程序路径、有效环境、策略检查、运行身份和失败语义没有被同一套行为契约完整约束。V2、V3 是具体例子。应先收敛这些接线点及公共入口测试；只提高行覆盖率或增加局部 helper 测试无法证明整条链路一致。

MLIP 的 runner 协议还需要区分“基础设施／后端失败”和“某个结构被丢弃”。错误行、done 文件、进程退出码和 durable completed 当前可以互相矛盾，这是 V1 的根因。

本轮沿入口、编译、组装、环境／策略、执行／取消／配额、续跑身份、artifact 验证、generation／publication、控制服务和结果投影检查关键链路。科学算法层结合类型、拓扑、结果消费路径和现有测试检查；未重新进行真实 ORCA、Gaussian、xTB 或 fairchem 的数值基准实验。

静态指标为 199 个生产模块、70,974 行；V4 静态可达 181 个模块、67,535 行。剩余 3,439 行只是该静态入口集合不可达，不能据此认定为死代码。R6 的性能优化仍维持此前“测量后暂不改”的决定，本轮未提供新的性能证据。

此前 D1–D5 与 A1 的相关回归测试均包含在本轮全量测试中；本轮没有足以重新打开这些问题的新证据。D3 维持此前评估结论。
